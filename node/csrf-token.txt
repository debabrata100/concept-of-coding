# CSRF Token vs Refresh Token

## Purpose

Although both are used in authentication systems, they solve different security problems.

| Token | Purpose |
|-------|---------|
| **Access Token** | Authenticates API requests. |
| **Refresh Token** | Obtains a new access token after it expires. |
| **CSRF Token** | Prevents Cross-Site Request Forgery (CSRF) attacks. |

---

# What is a CSRF Attack?

A CSRF attack occurs when a malicious website tricks a logged-in user's browser into sending requests to another website where the user is already authenticated.

Example:

1. User logs into:

```
https://bank.com
```

2. Browser stores:

```
refreshToken=abc123
```

3. User visits:

```
https://evil.com
```

4. Evil website submits:

```html
<form action="https://bank.com/transfer" method="POST">
    <input name="amount" value="100000">
    <input name="to" value="hacker">
</form>

<script>
document.forms[0].submit();
</script>
```

The browser automatically sends:

```
Cookie:
refreshToken=abc123
```

The attacker never sees the cookie.

However, because browsers automatically include cookies, the request appears authenticated.

Without CSRF protection, the bank cannot distinguish between a legitimate request and a forged one.

---

# Why Refresh Tokens Don't Prevent CSRF

A refresh token proves:

> "Who is making the request."

It does **not** prove:

> "Where the request originated."

If authentication relies solely on cookies, a malicious website can cause the browser to send those cookies automatically.

Therefore, refresh tokens do not stop CSRF attacks.

---

# What is a CSRF Token?

A CSRF token is a random value generated by the server.

Example:

```
csrfToken = 7d91f3a8
```

The token is sent to the frontend and must accompany every state-changing request.

Example request:

```
POST /profile

X-CSRF-Token: 7d91f3a8
```

The server verifies that the received token is valid before processing the request.

If the token is missing or incorrect:

```
403 Forbidden
```

---

# Typical Authentication Flow

## Login

Server responds with:

```
Access Token

Refresh Token (HttpOnly Cookie)

CSRF Token
```

Example cookies:

```
Set-Cookie:
refreshToken=abc123; HttpOnly; Secure; SameSite=Lax

Set-Cookie:
csrfToken=7d91f3a8; Secure; SameSite=Lax
```

Notice:

- Refresh Token is HttpOnly.
- CSRF Token is intentionally **not** HttpOnly.

---

# Why Isn't the CSRF Token HttpOnly?

JavaScript must read the token and include it in every request header.

Example:

```javascript
const csrfToken = getCookie("csrfToken");

fetch("/api/profile", {
  method: "POST",
  credentials: "include",
  headers: {
    "X-CSRF-Token": csrfToken
  }
});
```

If the CSRF cookie were HttpOnly:

- JavaScript could not read it.
- The header could never be added.
- Every protected request would fail.

---

# Why Can JavaScript Read the CSRF Token Safely?

A CSRF token is **not** a secret like a password or refresh token.

Its purpose is simply to prove:

> "This request originated from JavaScript running on my own website."

Because of the Same-Origin Policy:

- `evil.com` cannot read cookies belonging to `bank.com`.
- Therefore, it cannot obtain the CSRF token.

---

# Double Submit Cookie Pattern

A common implementation is:

```
Browser sends automatically:

Cookie:
refreshToken=abc123
csrfToken=7d91f3a8
```

JavaScript additionally sends:

```
X-CSRF-Token: 7d91f3a8
```

The server verifies:

```
Cookie csrfToken == Header X-CSRF-Token
```

If they match:

```
✓ Request accepted
```

Otherwise:

```
403 Forbidden
```

This is known as the **Double Submit Cookie** pattern.

---

# Express + React Example

```
React
│
├── Reads csrfToken cookie
├── Sends X-CSRF-Token header
└── credentials: "include"

        │

        ▼

Express
│
├── Reads refreshToken cookie
├── Reads X-CSRF-Token header
├── Verifies CSRF token
└── Processes request
```

# Do All Applications Need CSRF Tokens?

## JWT stored in Authorization header

```
Authorization: Bearer eyJhbGci...
```

Since browsers do **not** automatically attach the Authorization header:

- CSRF protection is generally unnecessary.
- Protecting against XSS becomes more important.

---

## Authentication using Cookies

```
Cookie:
session=...
```

or

```
Cookie:
refreshToken=...
```

Since browsers automatically send cookies:

- CSRF protection is recommended.
- State-changing requests (POST, PUT, PATCH, DELETE) should validate the CSRF token.

---

# Summary

| Component | Responsibility |
|-----------|----------------|
| Access Token | Authenticate API requests |
| Refresh Token | Issue new access tokens after expiry |
| CSRF Token | Prevent forged requests from other websites |

---

# Key Takeaways

- CSRF exploits the browser's automatic cookie handling.
- Refresh tokens authenticate users but do not prevent CSRF.
- CSRF tokens verify that requests originate from the legitimate frontend.
- JavaScript reads the CSRF token and sends it in a custom header.
- Refresh tokens should remain HttpOnly.
- CSRF tokens are commonly implemented using the Double Submit Cookie pattern.
- Applications using cookie-based authentication should implement CSRF protection.
- Applications using only the `Authorization: Bearer` header generally do not require CSRF protection.
