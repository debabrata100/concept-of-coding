# The complaint: "Users say typing in the search box on our dashboard is laggy. Every keystroke visibly stutters."
```
const ThemeContext = createContext();

function Dashboard() {
  const [query, setQuery] = useState("");
  const [theme, setTheme] = useState("light");
  const [orders, setOrders] = useState([]); // ~5,000 rows from API

  return (
    <ThemeContext.Provider value={{ theme, toggle: () => setTheme(t => t === "light" ? "dark" : "light") }}>
      <TopBar />
      <input value={query} onChange={e => setQuery(e.target.value)} />
      <OrderTable
        orders={orders.filter(o => o.customer.includes(query))}
        onRowClick={(id) => console.log("open", id)}
      />
      <Footer />
    </ThemeContext.Provider>
  );
}

  // renders all 5,000 <OrderRow /> elements, no virtualization

  const { theme } = useContext(ThemeContext);
  ...
});```

Profiler output for one keystroke:

Component	          Rendered?	    Why
Dashboard	          yes	          state changed (query)
TopBar	            yes	          context changed
OrderTable	        yes	          props changed: orders, onRowClick
5,000 × OrderRow	  yes	parent rendered
Footer	            yes	parent rendered

Your task, exactly as you'd say it out loud to the interviewer:

- Explain why OrderTable re-renders on every keystroke despite being wrapped in React.memo — there are - two separate prop-level reasons in that code; name both.
- Explain why TopBar re-renders on a keystroke that has nothing to do with theme.
- Then give your fix plan in priority order.

Ans: 
The full ordered fix plan you should say out loud:

- Move query state down into a new SearchableOrders component that owns the input, filtering, and the table. This shrinks the blast radius so keystrokes never touch Dashboard, TopBar, or Footer. This alone kills most of the lag.

- Memoize the context value with useMemo so theme-independent renders don't wake context consumers. (Even though point 1 already stops Dashboard from re-rendering on keystrokes, this is a defense-in-depth fix — the next developer will add state to Dashboard again eventually.)

- Wrap the filter in useMemo — 5,000-element filtering on every keystroke is expensive, and now the parent re-renders on every keystroke (that's inherent to the input), so we don't want to redo it unless query or orders actually changed.

- Stabilize onRowClick with useCallback so React.memo on OrderTable isn't defeated when SearchableOrders re-renders for reasons unrelated to the table's data.

- Virtualize the 5,000 rows with react-window or react-virtuoso. Even one legitimate re-render of 5,000 DOM nodes is slow — no amount of memoization fixes the render that must happen. This is the ceiling: without it, the app will still feel heavy on the first filter change even if everything else is perfect.

- Optional: wrap the filter update in useTransition so typing stays instant while the (now virtualized) list catches up as a lower-priority render.

The one thing to name at the end: the React Compiler would auto-handle steps 3 and 4 (the useMemo/useCallback plumbing), but steps 1, 2, 5, and 6 are structural decisions no compiler can make for you — which is exactly why "architecture beats memoization" is still the senior answer.
